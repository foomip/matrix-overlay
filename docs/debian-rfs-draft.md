# Request for sponsorship (Debian) - draft

The archive is the only route that puts `matrix-overlay` in the *default* COSMIC
Store catalogue: Pop!_OS inherits Debian and Ubuntu pockets, and COSMIC Store
reads the DEP-11 metadata of whatever repositories a machine already trusts. A
personal repository makes us installable today; `main`/`universe` makes us
installable for everybody. The request below is what a sponsor needs; nothing is
invented, and every claim points at a file in this tree.

Send it to the **sponsorship-requests** pseudo-package (Debian mentors):

```sh
apt install reportbug            # or use the web form / bts
reportbug sponsorship-requests --severity=important
# subject: RFS: matrix-overlay/0.1.1-1 - Matrix-style digital rain over every screen on COSMIC/Wayland
# body: the text below, plus the .dsc (debdiff against nothing for a new package)
```

Before sending: `lintian -i --pedantic matrix-overlay_0.1.1-1_amd64.changes` must
be clean (or each remaining tag explained in the body), and the autopkgtest must
have been run at least once (`autopkgtest mat'` in a container). Both are
checklist items below because neither tool is installed on the packaging box.

## Body of the request

I would like matrix-overlay packaged in Debian. I am the upstream author
(MIT, https://github.com/foomip/matrix-overlay), so licensing is unambiguous and
I can answer any upstream question in one reply.

**What it does.** A screensaver-shaped effect for Linux desktops: pressing a
shortcut dims the desktop and runs The Matrix "digital rain" across every
monitor; Escape, a click, or the same shortcut brings the desktop back. There is
no window and no tray icon - it is a layer-shell overlay, which is what makes it
work on Wayland at all (an X11 screensaver cannot cover a Wayland session:
Xwayland's root window is never composited).

**Why it is worth a place in the archive.** COSMIC (the default desktop of
Pop!_OS 24.04, and the desktop Wayland Fedora/KDE users are moving to) has no
screensaver of its own and no way to run an X11 one. This is the small utility
people ask for in desktop threads, and today the only answer is "compile
something and hope it works on Wayland".

**Technical shape.** A Python 3 package (the world model, glyph atlas,
configuration, CLI) plus a ~30 KB C client (`native/mwl.c`) that owns the
Wayland and EGL connection: one `zwlr_layer_shell_v1` OVERLAY surface per
output, GLES2 rendering into EGL windows the compositor imports as dmabufs. The
C part is why `Architecture: any`. It does not use GTK as a painter (measured:
GDK's per-frame shm copy pegged a core); a Cairo/GTK layer-shell painter is kept
as a fallback and its dependencies are `Recommends`, not `Depends`.

**Why it must not be a Flatpak.** cosmic-comp binds `zwlr_layer_shell_v1` with a
`client_not_sandboxed` filter, and Flatpak >= 1.15 always attaches
`wp_security_context_v1`, so a sandboxed build cannot create the overlay at all
(pop-os/cosmic-comp#2734; upstream's interim advice is to package shell
components with the distribution's package manager). Native packaging is the
correct shape here, not a shortcut.

**Quality.** 375 unit tests, headless by design (they need no compositor), a
live-session smoke test that asserts a frame-rate budget, and CI-style checks
that the version strings in `matrix_overlay/__init__.py`, `debian/changelog` and
the AppStream metainfo do not drift apart. The GPU selection logic (pick the
render node that actually drives a connected output) is documented and tested;
it is what makes one package behave on a hybrid machine and on an AMD-only
mini PC. `docs/` in the upstream tree documents the EGL vendor selection on
multi-vendor systems and the AppStream/DEP-11 publishing rules.

**Package details.**
- `debian/copyright`: MIT for the code; the three vendored protocol XMLs
  (`wlr-layer-shell-unstable-v1.xml`, `xdg-output-unstable-v1.xml`,
  `xdg-shell.xml`) keep their upstream copyrights and licences - the layer-shell
  one is the no-endorsement X11 text, not MIT - and are regenerated by
  `wayland-scanner` at build time, so the generated `*-client-protocol.{c,h}`
  files are not in the tarball.
- Build deps: debhelper-compat 13, python3, gcc, pkg-config, libwayland-dev,
  libwayland-bin, libegl-dev, libgles-dev.
- Runtime: `python3`, `python3-gi`, `gir1.2-glib-2.0`; Recommends for the
  fallback painter.
- `debian/watch` tracks the GitHub tags (`pgpmode=none` while upstream tags are
  unsigned - I will sign them and switch the field once a sponsor prefers it).
- `debian/upstream/metadata` records repository and bug tracker.
- `debian/tests/control`: one autopkgtest that exercises the *installed* package
  (`--help`, `--preflight`, asset placement, `readelf` hardening assertions). It
  deliberately does not start the overlay: a CI job with a compositor would be a
  flaky test. I would like guidance on running the full unit suite as an
  additional test entry - it needs `python3-pytest`, `python3-gi`,
  `python3-gi-cairo`, `gir1.2-gtk-3.0` and `fonts-noto-cjk`, and I would rather
  get the dependency set reviewed than guess it.
- `lintian`: see the checklist below; I will post a debdiff with each tag fixed
  or argued.

**What I need from a sponsor.** a review of the packaging (especially: the
Section choice `graphics`, the vendored protocol XMLs, the autopkgtest
dependency set), and a Salsa project so I can push VCS history
(`deb-scan`/`salsa:debian/*/matrix-overlay` if accepted).

**Who maintains it.** Me. I am reachable as `foomip` on GitHub; I will file the
`ITR`/`RFS` follow-ups and answer bug reports. I am not a DD.

## Pre-flight checklist (honest state, do not skip)

| Item | State |
|---|---|
| Package builds from a clean copy | verified (`packaging/publish.sh` builds in a temp tree) |
| Source format valid | `3.0 (quilt)` - the previous value `3.0 (native)` was not a real format and would have failed a source build |
| `dpkg-buildpackage -b` | clean, no warnings except `Priority` (documented in `debian/control`) |
| Standards-Version | 4.7.4 (Policy 4.7.4.1, 2026-03-31) |
| Unit tests | 375 green on x86-64, AMD and hybrid GPUs |
| Autopkgtest written | yes (`debian/tests/control`); **not yet executed** - needs `autopkgtest` + a container |
| `lintian` clean | **not run** - lintian is not installed on the packaging box |
| `uscan` reachable | **not run** - devscripts not installed |
| Reproducible builds | not verified (`rbenv`/`diffoscope` not installed) |
| Upstream tarball from a tag | GitHub serves `v<version>` tarballs; `debian/watch` matches them |
| ITR (intent to package) | not filed - optional, but polite for a new package |

Filing the RFS before the lintian and autopkgtest rows are green wastes a
sponsor's time; do those two first:

```sh
sudo apt install lintian devscripts autopkgtest
lintian -i --pedantic ../matrix-overlay_0.1.1-1_amd64.changes
uscan --verbose
# run the packaged autopkgtest in a clean environment (schroot, lxd or contain):
autopkgtest pkg/matrix-overlay -- schroot unstable-amd64-sbuild
# or, from this tree without installing the package into the testbed first:
autopkgtest --built-tree=.. pkg/matrix-overlay -- schroot unstable-amd64-sbuild
```
